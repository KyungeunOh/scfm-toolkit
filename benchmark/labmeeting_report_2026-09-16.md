# 랩미팅 보고 — scFM-toolkit 메모리 벤치마크 (2026-09-16)

발표 시간 목표: 5~10분. 아래 4개 섹션(배경 → 시도한 것 → 결과 및 해석 → 다음 단계) 순서로 말하면 됩니다.

---

## 1. 왜 이 작업을 하고 있는가 (배경, ~1~2분)

- 지난 진행상황 보고(9/9)에 대해 이제근 교수님께서 방향 전환을 지시하심.
  - **문제의식**: scfm-toolkit과 유사한 목적의 기존 도구가 이미 있음 — BioLLM(Patterns 2025, 통합 벤치마킹 프레임워크), scPEFT(Nature Machine Intelligence 2025, adapter 기반 PEFT로 파라미터 96%+·GPU 메모리 50%+ 절감). scfm-toolkit이 이들과 뭐가 다른지 분명히 해야 함.
  - **새 방향**: "사용자가 모델 + AnnData + 가용 GPU 메모리만 지정하면, 툴킷이 OOM 없이 fine-tuning 가능한 설정(precision, micro-batch size, gradient accumulation, activation checkpointing, LoRA rank, 입력 gene 수)을 자동으로 골라줄 수 있는가?" — 이게 실제로 가능한지부터 데이터로 확인하는 것이 지금 목표.
  - 이전 로드맵(6개 미구현 task: scGPT_CP, Integration, GRN, Multiomics, Perturbation, atlas 인덱스)은 **삭제가 아니라 일시 보류**.
- 대상 모델 2개, 이유가 다름:
  - **scGPT**: 상대적으로 작은 모델 → 비교 대조군.
  - **scFoundation**: 19,264개 유전자를 고정 vocab으로 다루는 구조라, 입력 gene 수가 늘어날 때 메모리가 급격히 증가하는 걸 보여주는 사례로 지목됨.
- 방법론 결정: LoRA/scPEFT를 scfm-toolkit 안에 새로 구현하지 않고, **scPEFT 공식 코드(github.com/laolintou/scPEFT)를 외부에서 그대로 돌려 비교군으로 사용**하기로 함(교수님 지시와 일치, 개발 시간 절약). scfm-toolkit 쪽은 "Full FT의 시스템 설정 축(precision/batch/grad_accum/checkpointing/gene 수)"만 담당.
- 측정 전략: 전 조합을 다 돌리지 않고, **먼저 큰 간격(coarse)으로 경향을 보고 OOM 경계 근처만 정밀 측정**하는 2단계 방식(교수님 지시).
- 타임라인: 약 2주로 논의됨(9/9 기준). 오늘은 그중 1주차 마무리 시점 — scGPT 인프라 구축과 첫 smoke test까지 완료.

## 2. 무엇을 시도했는가 (진행 내용, ~2~3분)

기존 GitHub 저장소(`main` 브랜치, 검증된 annotation 파이프라인)는 그대로 보존하고, **`memory-benchmark` 브랜치**에서 새로 개발:

1. **로깅 스키마** (`benchmark/run_log.py`): 교수님이 요구하신 항목(모델/체크포인트, cell·gene 수, precision, micro-batch, grad accum, checkpointing, 성공/OOM, peak allocated/reserved memory, 실행시간, macro-F1, 환경정보, seed 등 약 40개 필드)을 CSV 한 곳에 자동 기록하도록 스키마 고정.
2. **메모리 측정 인프라** (`benchmark/memory_probe.py`): `torch.cuda.max_memory_allocated/reserved`로 peak memory 측정. **OOM을 "실패"가 아니라 하나의 데이터 포인트로 처리** — OOM이 나도 프로세스를 죽이지 않고 CSV에 기록한 뒤 다음 조합으로 계속 진행. "12GB budget"처럼 메모리 제한을 흉내내는 기능도 포함(실제 GPU와 혼동되지 않게 별도 플래그로 구분).
3. **Coarse-then-fine grid** (`benchmark/grid.py`): `default_smoke_grid()`(최소 5개 조합, 처음 실행용), `coarse_grid()`(전체 조합), `refine_between()`(성공/OOM 경계 사이만 정밀 재측정) 세 가지로 교수님 지시 그대로 구현.
4. **scGPT adapter 확장**: 기존 검증된 fine-tuning 루프에 precision(fp32/fp16/bf16) 선택과 **activation checkpointing**(이 프로젝트에 없던 기능, 새로 구현)을 추가. 기존 동작(기본값)은 100% 그대로 유지되도록 하위호환 설계.
5. **scFoundation adapter 신규 작성**: 공식 저장소(biomap-research/scFoundation) 코드를 참고해 19,264-유전자 고정 vocab, `gatherData`(실제 발현된 유전자만 sparse하게 gathering — 이게 "gene 수 → 메모리" 관계의 핵심 메커니즘) 구조를 재현. 다만 기존 `ModelAdapter` 인터페이스(경로 1개만 받음)와 scFoundation이 필요로 하는 경로(3개) 시그니처가 안 맞아서, **`run.py` CLI 완전 통합은 후속 작업으로 분리**(scGPT/Geneformer에도 영향 주는 변경이라 신중한 별도 검토 필요) — 지금은 별도 sweep 스크립트로만 직접 호출. **아직 GPU에서 한 번도 실행 검증되지 않은 상태**(체크포인트/실행 환경 준비 전).
6. **실행 환경**: 기존 Docker 이미지(`scgpt-toolkit:v0.1`)를 재사용, `--entrypoint python` 오버라이드로 벤치마크 스크립트만 다르게 실행 — 이미지 재빌드 불필요(코드는 bind mount).
7. **서버 배포 중 발견/수정한 버그 3건** (모두 자체 발견, 실제 데이터를 신뢰하기 전에 처리):
   - 새로 만든 `benchmark/logging.py`가 파이썬 표준 `logging` 모듈 이름과 겹쳐서, 실행 시 표준 모듈을 가려버리는 문제 → `run_log.py`로 이름 변경.
   - sweep 스크립트가 기존 `run.py`의 로깅 설정을 안 가져와서, 학습 중 진행 로그(epoch별 진행 상황)가 전부 조용히 버려지던 버그 → 서버에서 "1시간 넘게 화면에 아무것도 안 뜨는" 상황의 실제 원인이었음(실제로는 정상 작동 중이었으나 확인할 방법이 없었음) → 수정.
   - 테스트 결과 보고 과정에서 제가 "34/34 통과"를 처음엔 "21/21"로 잘못 보고했던 것을 재확인 후 정정.

## 3. 어떤 결과가 나왔는가, 그리고 왜 (~2~3분)

scGPT 기준 5개 조합 smoke test 완료 (max_seq_len=3001 고정):

| precision | batch | grad_accum | checkpointing | 상태 | peak allocated | peak reserved | 소요시간 | accuracy | macro-F1 |
|---|---|---|---|---|---|---|---|---|---|
| fp16 | 1 | 1 | X | 성공 | 1.98GB | 3.64GB | 63.5분 | **2.3%** | **0.003** |
| fp16 | 8 | 1 | X | 성공 | 9.74GB | 10.29GB | 23.9분 | 87.7% | 0.790 |
| fp16 | 32 | 1 | X | **OOM** | 22.65GB | 23.46GB | 0.3초 | - | - |
| fp16 | 32 | 1 | O | 성공 | 6.17GB | 21.80GB | 29.8분 | 86.3% | 0.791 |
| bf16 | 32 | 1 | O | 성공 | 6.24GB | 21.84GB | 29.9분 | 87.6% | 0.748 |

### 3.0 표 항목 설명 (컴퓨터를 잘 모르는 사람도 이해할 수 있게)

- **precision**: 모델 계산에 쓰는 숫자 표현 방식. `fp32`(32비트, 제일 정밀하지만 메모리 2배), `fp16`(16비트, 메모리 절반이지만 표현 가능한 수의 범위가 좁아서 너무 크거나 작은 값에서 수치가 깨질 위험), `bf16`(16비트지만 표현 범위는 fp32와 같고 정밀도만 낮춤 — fp16보다 안정적, RTX 3090 이상에서 지원).
- **micro_batch_size(표의 batch)**: 한 번에 GPU에 동시에 올려서 처리하는 세포(cell) 개수. 이 숫자가 클수록 한 번에 쓰는 GPU 메모리도 커짐 — 이번 벤치마크에서 가장 중요한 축.
- **grad_accum_steps**: 배치 여러 개의 결과(gradient)를 모았다가 한 번에 모델을 업데이트하는 횟수. "GPU 메모리는 늘리지 않으면서 마치 더 큰 배치로 학습하는 것 같은 효과"를 내는 방법(예: batch=8을 4번 모으면 실질적으로 32짜리 배치처럼 학습됨).
- **activation_checkpointing**: 원래는 학습 중간 계산 결과(activation)를 전부 GPU에 저장해뒀다가 나중에(역전파 때) 씀. 이걸 저장 안 하고 필요할 때 다시 계산하는 방식으로 바꾼 것 — **메모리는 크게 아끼지만, 다시 계산하는 시간이 추가로 든다**("메모리 vs 시간"을 맞바꾸는 기법).
- **max_seq_len**: 세포 하나당 입력으로 넣는 유전자 개수. Transformer 모델은 이 길이가 늘어날수록 메모리·연산량이 훨씬 가파르게(길이의 제곱 정도로) 늘어남 — "gene 수를 늘리면 메모리가 급증한다"는 교수님 지적이 바로 이 부분.
- **status**: `success`(정상 완료) / `oom`(GPU 메모리 부족으로 실패 — 이 프로젝트에서는 "버그"가 아니라 정상적인 실험 데이터로 취급) / `error`(그 외 예외 — 코드/설정 버그 의심).
- **peak_allocated_mb**: 실행 중 실제로 데이터(모델 가중치+중간 계산값+gradient) 저장에 쓰인 GPU 메모리의 최댓값. "진짜 필요했던 메모리"에 가장 가까운 수치.
- **peak_reserved_mb**: PyTorch가 CUDA로부터 미리 확보해서 캐시로 들고 있는 전체 메모리 풀의 최댓값. 메모리를 매번 반납/재요청하면 느려지니 한 번 확보한 걸 계속 들고 재사용하는 방식이라 **항상 allocated보다 크거나 같음**.
- **total_seconds(소요시간)**: 이 설정으로 지정된 epoch 수(10회)만큼 전체 학습을 끝내는 데 걸린 시간.
- **accuracy**: 예측이 맞은 세포 비율.
- **macro_f1**: cell type 18종 각각의 F1-score(정밀도·재현율을 합친 지표)를 단순 평균한 값 — 세포 수가 적은 희귀 타입도 흔한 타입과 동일한 비중으로 반영되므로, accuracy보다 "골고루 잘 맞히는지"를 더 엄격하게 보여줌.

### 3.1 각 행이 왜 이렇게 나왔는지

- **fp16/batch=1**: 메모리는 제일 작음(1.98GB, 세포 1개만 올리니 당연). 그런데 시간은 제일 오래 걸림(63.5분) — 세포 1개씩 처리하면 GPU 코어를 거의 못 놀리는 셈이라 비효율적이고, 21,312개 세포 ÷ 배치 1 = 스텝 수 자체가 압도적으로 많음. accuracy 2.3%는 아래 3.2에서 별도로 다룸.
- **fp16/batch=8**: allocated가 9.74GB로 batch=1의 약 5배 — 배치가 8배 커졌으니 저장해야 할 중간 계산값도 그만큼 늘어난 것. 시간은 23.9분으로 batch=1보다 훨씬 짧음(스텝 수가 1/8로 줄고 GPU 활용도 좋아짐). accuracy 87.7%/F1 0.790으로 정상적인 좋은 결과 — 지금까지 중 가장 "무난하게 잘 된" 조합.
- **fp16/batch=32, checkpointing 없음 → OOM**: 22.65GB까지 찍고 0.27초 만에 실패. 이 22.65GB는 "끝까지 처리했다면"의 값이 아니라 **OOM으로 멈추기 직전 순간의 스냅샷**이라, 실제로 32개를 끝까지 처리할 수 있었다면 이보다 더 큰 메모리가 필요했을 것. 0.27초 만에 죽었다는 건 모델 로딩까지는 성공했고 첫 배치를 처리하는 도중 바로 24GB 한도에 부딪혔다는 뜻.
- **fp16/batch=32, checkpointing 켜짐**: allocated 6.17GB로 batch=8(9.74GB)보다도 오히려 적음 — checkpointing이 중간 계산값을 저장 안 하고 다시 계산하는 방식이라, batch가 4배 커졌어도 "저장해야 하는 양" 자체가 훨씬 적어진 것. 대신 시간은 29.8분으로 batch=8보다 조금 더 걸림(다시 계산하는 비용 + batch 4배 증가가 섞여서 나온 순증가). accuracy/F1은 batch=8과 비슷한 수준(86.3%/0.791) — checkpointing은 "저장 방식"만 바꾸는 것이라 계산 자체는 동일하므로 성능에 나쁜 영향이 없는 게 정상.
- **bf16/batch=32, checkpointing 켜짐**: 메모리(6.24GB)·시간(29.9분) 모두 fp16과 사실상 동일 — bf16도 16비트라 메모리 사용량 자체는 fp16과 같고, 차이는 표현 범위/정밀도뿐이라 메모리에는 영향이 없는 게 정상. accuracy는 fp16보다 살짝 높고(87.6%) macro_f1은 살짝 낮은데(0.748), 이 정도 차이는 한 번 학습한 결과이므로 시드(무작위 초기값)에 따른 우연한 변동일 가능성이 높음 — 결론 내리려면 여러 시드로 반복 실행해서 재현되는지 봐야 함.

### 3.2 이상치 상세 — batch=1 accuracy 2.3%

18개 cell type을 완전히 무작위로 찍어도 평균 5.5% 정도는 맞아야 하는데 2.3%는 그보다도 낮음. 후보 원인: (1) batch=1이라 매 스텝의 gradient가 세포 1개짜리라 극단적으로 노이즈가 크고, 이 노이즈가 fp16(표현 범위가 좁음)과 만나 학습 중 loss가 발산(nan/inf)했을 가능성, (2) 순수하게 batch=1 자체의 학습 불안정성(코드 버그는 아님). 지금까지는 이걸 구분할 방법이 없었는데, 코드에 진단 로그를 추가했다(4절 참고) — 다음 실행에서 "loss가 nan/inf였던 스텝 수"가 로그에 찍히면 (1)번이 원인, 안 찍히는데도 계속 낮게 나오면 (2)번 쪽에 무게가 실림.

### 3.3 이상치 상세 — peak_reserved가 조합 간에 비정상적으로 비슷함

reserved/allocated 비율을 조합별로 계산해보면 패턴이 뚜렷하다: batch=1(1.84배), batch=8(1.06배), OOM 조합(1.04배)까지는 비율이 정상 범위(보통 1~2배)인데, 그 **다음에 실행된** checkpointing 두 조합만 3.5배(21.8GB÷6.2GB)로 튄다. 5개 조합이 전부 같은 프로세스 안에서 연달아 실행됐고, 마침 batch=32/OOM 조합이 GPU 메모리 거의 전부(23.46GB)를 요청했다가 실패한 직후에 이 두 조합이 실행됐다는 점이 우연으로 보기 어렵다 — **OOM 조합이 확보했던 대용량 메모리 캐시가 완전히 반납되지 않고 다음 조합들에 그대로 남아있었을 가능성이 높다.** peak_allocated_mb(실제 필요 메모리, OOM 판단 기준)에는 영향이 없지만, reserved 수치를 정밀 비교하려면 조합마다 프로세스를 격리해야 한다 — 이것도 코드로 수정함(4절).

**참고**: smoke 5개 조합에 총 2시간 반 정도 소요(batch=1 조합이 대부분을 차지) → 전체 coarse grid(144개 조합)를 그대로 다 돌리는 건 비현실적임을 확인. "coarse→정밀" 2단계 전략이 실제로 필요하다는 걸 재확인.

## 4. 다음 단계
